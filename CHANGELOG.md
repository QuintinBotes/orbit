# Changelog

## Unreleased

- Tests in C#, F#, Visual Basic, Java, Kotlin, Scala, Groovy, Rust, Ruby, PHP, Swift, C and C++, Elixir and Dart are recognised (#30, ADR 0011). Test files were recognised only for .js/.ts/.py/.go/.vue/.svelte, so a candidate that added xunit tests "added or changed no test": every criterion whose check already passed on the base revision was unverified with "no new evidence", and the run ended BLOCKED. One set of rules now serves the new-evidence rule, the weakening signals, the unexplained-architecture trigger and the review packet, and follows each language's test runner: a .NET source counts when the project that owns it on each revision is a test project by its project file (IsTestProject, or a Microsoft.NET.Test.Sdk, xunit, xunit.v3, MSTest or TUnit reference, or a legacy test framework Reference; nothing under a condition), so neither a test-named file of a production project, nor a test project added around production files, nor a library that references only NUnit or MSTest.TestFramework (which `dotnet test` does not run) counts; JVM sources count in a test source set (`src/test/` and its Gradle, Android and Kotlin Multiplatform variants), not a helper source set or a source set's `resources/`; Rust counts a crate's `tests/` and a `#[test]` function, not ignored, that the change adds to a source cargo compiles (a crate root or a declared module of the crate's `src/`), so a test beside a `[workspace]`-only manifest, in `benches/` or in an undeclared file is not new evidence; the test attribute is judged by its whole attribute group in the candidate, so changing only the attribute of a test whose `#[ignore]` is unchanged (made async, or given another `test_case` row) is not new evidence either, and neither is a test in a comment or string, under a `cfg` other than `cfg(test)`, or in a module such a `cfg` leaves out. The weakening signals count a file that was a test on either revision, so changing a test project's file does not hide the tests deleted beside it. The layout is read from the directories above the changed files only, so a repository whose full listing is larger than 8 MiB no longer loses its test projects.
- A check the contract requires that the base revision had not run is run there before any change is judged (#32, ADR 0012). With `checks.format.mandatory: false`, which `orbit doctor` advised for a `dotnet format` check that cannot run in the macOS check sandbox, PREFLIGHT skipped the check, the planner cited it in an optional criterion (`contract.check-added: format`), and on the candidate it failed on the sandbox's refused named pipe. The base revision had no result for it, so the candidate gate (ADR 0010) could not tell the environment from the code: the run went to diagnosis and a repair on an identical tree and ended `EXHAUSTED`, unexplained. Now PLANNING runs every check the contract requires that the baseline has no result for on the base revision, before any attempt, and VERIFYING does the same for a check a contract amendment adds later (a baseline amendment, recorded in `baseline.json` and as a `baseline.amended` decision; its checkout installs the locked dependencies again rather than reusing PREFLIGHT's record, as a resumed PREFLIGHT now does too). Each is classified as PREFLIGHT classifies a mandatory check: an environment failure or a misconfigured check blocks the run there, with PREFLIGHT's reason and a sentence that says the contract requires the check, and `orbit resume` after an environment fix runs it again; a missing target is settled against the contract, while the contract requires the check (an approved amendment that stops requiring it leaves nothing to block on); a pre-existing failure gets its baseline-exception question, withdrawn when the contract names the check as a proof; a pass makes a failure on a candidate the change's. The `baseline.amended` decision is recorded once the amendment is judged, and an amendment cut short before that is amended and judged again on the next pass, so a pre-existing failure it found is still asked about. The planner may still name an optional check, and is told that naming one runs it on the base revision first. Doctor's fix for a `dotnet format` check that cannot run no longer offers `mandatory: false` (remove the check and run it in CI), and an optional such check warns that a run whose contract requires it would block at its baseline.
- A repair attempt that ends on a tree an earlier attempt produced, which verification judges `FAIL` exactly as before, ends the run `EXHAUSTED` as non-progress at once (#32, ADR 0012). The same tree is the same candidate, whose recorded check results are reused, so the repair loop kept asking for a diagnosis and dispatching implementers that could not change the outcome, until the non-progress threshold or the attempt budget stopped it. A new tree, a changed judgement, a resume or `orbit repair` since the attempt started, or a repair session that stopped before it finished (max turns, a timeout, a failure, malformed output) keeps the loop, and an open material question blocks the run for its answer instead; the budget rules are otherwise unchanged. `orbit repair` on a run paused in DIAGNOSING now records the request too (`run.repair-requested`), which it did only when it moved the run there.
- Accuracy and wording found by the 0.2.1 retest (#33, ADR 0013). Doctor: `checks.sandbox` no longer says that a run would block at its baseline for a refused check that is not mandatory, which PREFLIGHT does not run, but that a run whose contract requires it would (it runs there first, #32), whatever the sandbox refuses it for, and it no longer offers "set mandatory: false" to a check that has it (the fix for a `dotnet format` that cannot run is to remove it, #32); `checks.dotnet-packages` reports a cache that holds packages as filled, a pass with no fill command, and warns only for an empty cache or a floating version; the fix and the toolchain line no longer say the dependency install restores from, or fills, the cache when Orbit skips its own install ("no lockfile to install from", and `npm ci` restores no NuGet package), but say what does; `claude.plugins` says workers "would load" only a managed plugin and "may load" one of a scope it cannot place (such as `synced`, which sessions were seen not to load), and that a report lists the plugins its sessions reported loading and says nothing when they loaded none.
- The CLI's closing line, `orbit status` and the report no longer advise `orbit resume` where only a new run helps: an environment block of a candidate's check with no baseline exception to approve, and a frozen-policy block with a question open (`orbit status` says "a new run is needed" and why, in place of "will return to VERIFYING"; for a frozen setting that a fix outside the policy clears, such as `providers.<x>.model` after `orbit models refresh`, it also names `orbit resume --force`, as the outcome reason does). The notification says the same. A run whose attempt counter is full is not one of these: the counter is charged when an attempt starts, so a run that blocks in the middle of its last attempt (an authorization to answer, an expired login) resumes into that attempt and finishes, and keeps "answer, then resume".
- `gate.baseline`, `baseline.recorded` and `baseline.json` agree: a baseline in which a check never produced a result of its own (the environment stopped it, or its command was rejected) is incomplete in all three, so the gate is `unverified` where it was recorded as `pass` and the event said `complete: true` just before the run blocked. `gate.baseline` is recorded as `not applicable` when nothing ran on the base revision (no mandatory check, no locked install, no audit), where it said `pass` with "0 check(s)", and a baseline amendment the run goes on from records it again with the checks it ran. `gate.ui` is recorded as `not applicable`, citing no evidence, when nothing needs UI evidence, and its reason is not listed as "Not verified" (the evidence report, `final.json` and `final.md`, the pull request body and `orbit verify` leave it out: nothing was checked, and nothing was left unchecked).
- A run that ended before any worker session (blocked at PREFLIGHT) starts no curator, and says why in `learning.json`; `orbit report`'s cost includes the curator's, as status and the timeline do, because the final report is written again once it is charged.
- `orbit init` says the template it writes sets `providers.codex.data_policy_eligible: false`, so Codex does not review until it is set to true, and no longer tells a configuration that already defines checks to define them, also when it fails validation for another reason (it then says to fix the listed problems; `checks_defined` in `--json`).
- `orbit status`, the report and a succeeded run's notification name the candidate ref that exists (`refs/orbit/<run>/candidates/<n>`, `candidate_ref` in their JSON) in place of a branch `orbit/<run>` for a run that never delivered, where no such branch was made; `branch` is set only once delivery created it: by a local delivery whose gate passed (a refused one now leaves no branch behind, where the branch was made before the gate ran), by a successful push (a delivery that pushed and then failed at the pull request or the gate no longer reports "no branch"), or by a recorded delivery. The route reason of an unvalidated model says nothing has validated one yet instead of quoting the router's "no eligible claude-cli model" while choosing the model, and where a model is validated and the router still found none eligible (a tier it does not justify) it says the model was chosen although the router reported that, not that nothing is validated.
- `orbit doctor` says when workers cannot run a repository's tests because they cannot listen (#31). In a .NET retest five of six implementers ran their own `dotnet test -m:1`, which built and then aborted with `SocketException (13): Permission denied` at `Socket.Bind`: VSTest listens on loopback for its test host, and neither worker tier lets a worker listen. The workers reported their tests as not run, and the checks, which may listen by their `local_binding`, ran the same tests. Letting workers listen was measured and refused: on macOS 27 with `srt` 0.0.78 and Claude Code 2.1.292, `allowLocalBinding` lets a sandboxed process listen on every address of the machine, and a listener on 0.0.0.0 or `::` answered a connection made to the machine's network address. Seatbelt has no narrower rule: one for `"localhost"` admits 0.0.0.0 and the network address too, a numeric address is refused, and a connection's peer is never checked. Workers run model-driven commands, so on macOS a worker still may not listen, in either tier: the Claude worker settings now write `sandbox.network.allowLocalBinding: false` (held there by their schema), and the adapter hands `srt` none whatever profile it gets. On Linux every sandbox has a loopback of its own (`srt`'s source always starts `bwrap --unshare-net`; not measured on Linux), so workers there can run these tests. `orbit doctor` (`workers.loopback`) warns on macOS for a .NET or Gradle repository that workers cannot run test hosts that need a loopback socket, in either tier, and names the test checks that run them. A check's `local_binding` is unchanged: on macOS its listener is not limited to loopback either, and it reaches services on any address of the machine over TCP and UDP, as since the first live run, now stated in docs/security.md with the measurements (ADR 0001, "Workers and loopback").
- A worker cannot read the token of an IDE extension's MCP server (#31, review). VS Code's and JetBrains' Claude Code extensions write `<config dir>/ide/<port>.lock` with the token of their server on loopback, whose tools edit files in the editor and run code in a Jupyter kernel outside any sandbox, and Claude Code also looks in `~/.claude/ide` when `CLAUDE_CONFIG_DIR` is set. While a draft of this change let workers use loopback, a worker read the token (its Bash in the `os-sandbox` tier, the Read tool in the `claude-sandbox` tier) and the server accepted it. A check cannot read the lock, since its profile denies every Claude config directory, but on macOS a check that may listen can reach loopback and runs the code a worker wrote, so a token the worker copied into the worktree would reach the server through it. The worker profile now denies `<config dir>/ide` for reading and writing and every other Claude login Orbit knows of (`CLAUDE_CONFIG_DIR`, `~/.claude`) whole, and the worker settings deny `Read` on all of them in both tiers, so with `CLAUDE_CONFIG_DIR` set the Read tool no longer returns a token from `~/.claude/ide` in the `claude-sandbox` tier; the guard hook refuses `~/.claude/ide` too. A lock directory Orbit cannot know of (a config directory set only in the editor's environment) is not covered. The worker's own `.claude.json` stays readable to it (the CLI needs it), with any MCP server headers you put there (docs/security.md).
- Background tasks are off for Claude workers (#31, review). `claude -p` does not exit after its result while a background task is alive, so a long command (`run_in_background`, or a foreground command the CLI moves to the background at its timeout) held the session until the role's time limit, which ended as a `timeout` and went to diagnosis though the work was done. `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` removes `run_in_background` and ends a foreground command at its Bash timeout, and the implementer and diagnosis prompts say to start and stop a server within one command. A process a worker detaches itself (`nohup`, `setsid`) still outlives the session on macOS, with the worker's sandbox, so it can go on writing the worktree after the session (docs/troubleshooting.md).
- `orbit doctor` says when workers cannot build or test a repository's toolchain (#31, review): `workers.toolchains` warns in the `claude-sandbox` tier for Go, Rust and the JVM, whose build state (`GOCACHE`, `CARGO_TARGET_DIR`, `GRADLE_USER_HOME`, Maven's local repository) Claude Code's sandboxed Bash cannot write there, so a worker's own `go test` or `cargo test` fails before any test runs while the checks pass. `workers.loopback` and `workers.toolchains` are reported only when the config could be read, like doctor's other config lines; `workers.loopback` reported a pass for the default config when `.orbit/config.yaml` was invalid.

## 0.2.1 (2026-10-07)

- A worker's, approved operation's or release command's private temp directory is checked before it is reused: a link or a file left in its place is removed, and a directory owned by someone else is refused, so the sandbox never grants writes through it.
- Approved operations, the UI application and release commands get the toolchain profile a check gets (#26). Each built its sandbox from the check profile alone, so .NET there had no NuGet cache, no NIS domain name rule and no `-m:1` handling. Measured under `srt` on macOS (SDK 9.0.305): an approved command and a deploy, each with a fresh private home, died at the SDK's first run on every dotnet command (`'NuGet-Migrations'`, the mutex under `/tmp/.dotnet`); `ui.environment.start_command: [dotnet, run, --project, Web]` for a web project referencing two libraries was never ready ("(no output)" after MSBuild's node retries); and built with `-m:1` first, its host hung at startup and its `HttpClient` died on `GetDomainName: -1`. Now each finds its toolchains from its command and the checkout as a check does: the repository's dependency caches read-only, build state private to the command, NuGet's audit decided by the hosts its sandbox allows, and for .NET a private home prepared as a check's, the NIS rule and IPv4 sockets on macOS, and the runner's early stop when MSBuild records a refused worker node, with a note naming the fix for that command's field. A deploy stopped that way fails (`srt` exits 0 when stopped, which no longer reads as deployed), a verify command whose build was refused leaves the deploy UNKNOWN, and an application stopped that way ends the UI run at once instead of after `ready_timeout_seconds`. A release command and an approved operation, which may fetch on the hosts their sandbox allows, write dependency caches of their own (removed after the command), with the repository's read-only beneath them where the tool reads a second cache: `NUGET_FALLBACK_PACKAGES`, a `GOPROXY` whose first entry is the repository's module cache, and Gradle's and Maven's read-only layers; Cargo and pip start empty there, as under the private home they had before, so a Rust or Python deploy needs its registry hosts in `network_hosts`. Each finds the host's rustup installation as a check does, in `RUSTUP_HOME` of the controller's environment, else in `~/.rustup` of the account's home (also when the caller names no home, as the sandbox profile already assumed), so rustup's `cargo` proxy finds its toolchain under the command's private home: on GitHub's runners a deploy `cargo install --path . --offline` failed with `rustup could not choose a version of cargo to run`. With the check's read-only caches alone they could fetch nothing: under `srt` on macOS a deploy `go run .` that fetched one module from a proxy in the repository failed with `go: writing go.mod cache: mkdir <orbit home>/toolchains/<key>/gomod/cache: operation not permitted`, and a NuGet restore from a feed in the repository and `cargo install --path .` were refused the same way, which would have failed every deploy or verify command needing something the run's install did not fetch (a deploy tool in another toolchain, `go run tool@version`, a merge commit's new package). An approved command that is itself a package install with a toolchain it uses, such as `dotnet add package`, is the install for that toolchain and may write the repository's cache of that toolchain only, on the policy's hosts plus the approved one, and its output says whose cache was writable. An approved command Orbit stopped (a refused node, the run's cancellation, the time limit) has no exit code in its receipt, where a cancelled one read exit 0, and a command that exited on its own before Orbit's look no longer reads as stopped. A deploy's and a verify command's temp directory, and the UI run's, are emptied before each use, so a node report an earlier invocation left cannot decide a later one. The application keeps the account's Python user site-packages (no private `PYTHONUSERBASE`). `orbit doctor` (`checks.sandbox`) judges `ui.environment.start_command` and, in mode `release`, each release environment's `deploy_command` and `verify_command` with the .NET rules (`-m:1`, `dotnet run` in two steps, `dotnet format`), as mandatory, with argv-ready fixes (`["sh", "-c", "dotnet build Web -m:1 && dotnet run --project Web --no-build"]`). Every .NET process under `srt` on macOS also gets `DOTNET_USE_POLLING_FILE_WATCHER=1` unless it sets the variable: the sandbox denies the FSEvents service a native file watcher asks, and ASP.NET Core's host hung on it (ADR 0009 addendum, items 14 to 16).
- `orbit run` no longer starts a run whose worker sessions would all be refused for a plugin the policy does not allow (#22). `orbit doctor` failed `claude.plugins` for the managed plugins that the defaults (`agents.allowed_plugins: []`, `agents.allow_managed_plugins: false`) refuse, yet `orbit run --foreground` went on: about ten minutes of base-revision checks, baseline-exception questions and a planner worker, then two refused planner attempts and a refused curator (about 0.8 USD, nothing produced). Run start now makes doctor's judgement (one shared function, `judgeWorkerPlugins`): `orbit run --foreground` refuses in admission, before a run row, a frozen policy, a check or a model call exists, with every plugin id and doctor's exact fix line (exit 4, "No run was created"); a run handed to the service (`--detach`) or resumed is judged by its controller at the start of PREFLIGHT, before the base-revision checks, and ends BLOCKED with nothing spent (no check, no question, no worker, no curator). Why two places and not one: only the process that drives a run can judge its Claude Code environment, and a run that exists has already frozen the policy the fix would change, so refusing before it exists is the clean outcome whenever this process drives it; a BLOCKED run that cost nothing is the fallback when only the service can judge, and its message says the way out (allow the plugin and start a new run, or remove the plugin and `orbit resume --force`).
- A worker session that Orbit refuses after it started (a plugin the policy does not allow, an MCP server, another permission mode) is not transient and is no longer retried as a worker attempt (#22): the planner, the reviewer and diagnosis units, and the implementer (also a parallel work unit) end the run BLOCKED after that one session. The outcome line carries the whole refusal, naming every plugin and the config line that allows it (it was cut at 200 characters, mid-sentence), and says that `orbit doctor` shows the cause. A run that ended this way with no candidate does not start the curator, which would be refused in the same environment (`worker_refusal` in the run outcome, "refused" in `learning.json`).
- `orbit init` in a linked git worktree says that the exclude file it wrote is shared (#3 follow-up). git reads only the common git directory's `info/exclude`, so the rules always went to the main checkout's `.git`, outside the worktree, which surprised a person who expected init in a worktree to change nothing outside it. Orbit keeps that shared write (one write covers every worktree, nothing is committed) and now names the file and states that every worktree of the clone shares it, both when it adds the rules and when they are already there. `orbit init --json` gains `exclude_file` (`path` and `shared_across_worktrees`, true in a linked worktree and false in a normal checkout; detected with git by comparing `--git-dir` with `--git-common-dir`); `exclude` keeps its `path` and `added`. A normal checkout prints what it always did.
- PREFLIGHT classifies every check that fails on the base revision before it calls one pre-existing (ADR 0010), and only a usage error from the check's own direct invocation of a tool counts: the command's program (after a leading env assignment, `env`, an npx-style runner or `python -m`) is the tool, the command is not a shell chain or pipeline, and what the error names is what the command names. An argument error (MSBuild's `MSB1001` outside `dotnet test` and `MSB1008`, go's undefined flag or unknown command, cargo's unexpected argument) is a misconfigured check: the run blocks at PREFLIGHT with the check, the tool's error line and `checks.<id>.command`, as a frozen-policy block whose advice names a new run, not `orbit resume --force`, which runs the same command again and so blocks again unless the tool changed outside the policy; before, it was offered as a baseline exception (#23). A missing target (MSBuild's `MSB1003`, `MSB1009` and `MSB1011`, `dotnet test`'s `MSB1001` (a test platform's option such as `--report-trx` before the repository runs that platform), npm's `Missing script` for the script the command runs when npm ran no script before it (no `> acme@1.0.0 test` banner), pytest's file or directory not found and its unrecognized arguments with exit 4 (an option of a plugin or `conftest.py` not there yet, such as `--cov` without pytest-cov or `-n` without pytest-xdist, which a goal may add), dotnet's or cargo's unknown command, a script of the repository the shell cannot find) goes on to CONTRACTING: when the contract names the check as the proof of a criterion its question is withdrawn and it is expected to flip, otherwise the run blocks there as misconfigured, with advice of its own by cause (a goal meant to create the target says so in a new run, a target a tool provides that is not installed or restored yet, such as a cargo plugin, a dotnet local tool or a pytest plugin, needs a new run once it is, a wrong command is corrected in `checks.<id>.command`; never `orbit resume --force`, which reads the same recorded baseline and blocks again), before the contract is written or any other check's question is settled. `orbit resume` refuses that block (exit 5) with the same advice and the foreground summary points to it, instead of sending a person to fix `.orbit/config.yaml`, which is the cause in one of the three; the notification of any frozen-policy block says to read the report, not to resume; and the outcome reason a run row keeps is cut in its evidence, never in the advice that ends it. A program the shell cannot find (exit 127) is an environment failure, cleared by installing it and `orbit resume`. An environment failure now also covers EACCES ("Permission denied") outside the checkout, a socket refused in a .NET tool's own crash (`MSBUILD : error MSB1025` with `SocketException (13): Permission denied`, reproduced under `srt` on macOS from `dotnet test` of a project with two references; the fix named is `-m:1` on a dotnet command that hands its arguments to MSBuild, as in the .NET entry below, and for `dotnet format`, which takes no `-m:1`, the check's command in the form that loads no project, as in the `dotnet format` entry below), a connection the sandbox's network proxy refused, NuGet's HTTP client failing to start in the sandbox (which the NIS domain name rule below prevents under the `srt` Orbit ships), and NuGet's restore that could not establish the SSL connection to nuget.org (on macOS nothing in the sandbox can verify its certificate; a review reached it as a pre-existing failure with a question by following the fix for the proxy's refusal, whose fix for a NuGet restore on macOS is now the cache filled outside the sandbox, and `checks.dotnet-packages` now fails when a mandatory check restores into an empty cache); MSBuild's `N Error(s)` no longer hides a restore the sandbox or its proxy refused on the base revision when every counted error is a restore error (`NUxxxx`) or `MSB1025` (on a candidate that count stays the change's unless its base revision failed the same way). Such checks block with the first error line and a fix instead of becoming pre-existing failures with questions (#10); checks that share their evidence are named once, then the evidence once, and every sentence of a block reason starts with a capital letter. On a candidate those new denials count only when the same check showed the same one on the base revision, so a denial the change brings (a test that opens a file it may not read, a package from a host the check may not reach) goes to repair; Python unittest's `FAILED (errors=1)` and `ERROR: test_x (...)` now read as a failing test, as do Microsoft.Testing.Platform's report (`failed X (12ms)`, `failed: 1`, printed by xunit v3, MSTest's runner and TUnit) and xunit's own (`[FAIL]`, `Failed: 1,`), go test -json's `"Action":"fail"`, bun's `(fail)` and dart's `Some tests failed.`, so a test that fails on a path it may not read stays the code's, on the base revision and in repair; a footer-like line a check prints is its own output, only the log's last line is the runner's. The planner is told which checks are missing targets, and a baseline-exception question raised before this change is refused for a failure the environment stopped, read again from its log. None of these can be accepted as a baseline exception through `orbit decide` or a remote answer, a missing target included. A usage error printed by a script of the repository (`npm test` whose script runs a missing `npm run lint`, or `cd client && npm test` in a package with no test script), a chain (`dotnet restore && npm test`) or a program the check runs (`dotnet run --project build/...`) stays a pre-existing failure, as does output with a compile error or a failing test. `orbit timeline` names each check's classification and first error line, and a resumed baseline runs those checks again instead of reusing the failure it recorded before the fix.
- .NET checks that build more than one project now run under `srt` (#10, reopened). MSBuild started a worker node for any restore or build with two projects to work on, and the node's named pipe (a Unix socket at `/tmp/MSBuild<pid>`) is refused by the sandbox: on macOS MSBuild then waited 30 s for each of ten node starts and failed after five minutes (`MSB1025` and `SocketException (13): Permission denied` from `dotnet test`), on Linux it failed at once with no error. A dotnet check now pins one node in its own command with `-m:1`; Orbit does not change a check's processor count, since `DOTNET_PROCESSOR_COUNT=1` would reach the test host, where xunit before 2.8 deadlocks a test that blocks on async code. `orbit doctor` fails a mandatory check (or `dependencies.install_command`) that runs `dotnet build`, `test`, `publish`, `pack`, `restore`, `clean`, `msbuild` or `run` itself (its command, the command `env` starts, or a command of a chain joined by `&&` or `;`, `sh -c` included) without `-m:1` before any `--` of `dotnet test`, unless its own `env` sets `DOTNET_PROCESSOR_COUNT=1`, before starting anything, and prints its command with `-m:1` added (for `dotnet run`, a build with `-m:1` and a run with `--no-build`, which it then passes), with the reason once for all such checks; it warns that it cannot tell for a check that runs MSBuild through make, a script or a shell line with a pipe or other shell syntax. A check that starts a worker node anyway is stopped as soon as MSBuild records the refused node, with the pipe and the fix for its command in its record, instead of after five minutes, and that record is read as the environment's failure (`pipe-denied`): on the base revision the run blocks at PREFLIGHT with the fix and no baseline exception question. On a candidate it counts only when the same check showed it on the base revision, as for the denials ADR 0010 added: a node the base revision did not start is the change's (a second project under a check without `-m:1`, a test that runs `dotnet build`), and it goes to repair. `orbit doctor`'s .NET line now builds three generated projects (offline, no packages) in the check sandbox with the node switches MSBuild gets from that check's command, in its env, instead of running `dotnet help`. `orbit init` proposes `dotnet build <target> -m:1` and `dotnet test <target> -m:1`. Workers in a .NET repository under `srt` are told to pass `-m:1` (a worker's `dotnet build` without it waited the same five minutes). `checks.dotnet-tests` warns when a check relies on `DOTNET_PROCESSOR_COUNT=1` in its own `env` and a test project uses xunit before 2.8. A toolchain the sandbox refuses, of any kind, now fails doctor instead of warning when a mandatory check runs its executable itself (ADR 0009 addendum).
- .NET HTTP clients now work under `srt` on macOS. Each one reads the NIS domain name when it starts, which `srt` refused, so NuGet's restore failed with `NU1301 ... The type initializer for 'System.Net.CookieContainer' threw an exception ... GetDomainName: -1`, as did any test that makes an HTTP request. Orbit's preload adds one read-only Seatbelt rule, `sysctl-read` of `kern.nisdomainname`, to the checks, the dependency install, workers and doctor's probes that run .NET (with `srt` 0.0.78; with another version the record says it was not added), and to approved operations, the UI app and release commands (see the toolchain profile entry above). Those processes also get `DOTNET_SYSTEM_NET_DISABLEIPV6=1`, unless their command sets it: .NET opens dual-stack IPv6 sockets, so a connect to loopback arrives as `::ffff:127.0.0.1`, which `srt`'s Seatbelt loopback rule does not match on some macOS releases (GitHub's macOS runner; macOS 27 matches it), and there every .NET HTTP request in the sandbox, NuGet's restore through `srt`'s proxy and a test's request to its own server on loopback, failed with `Permission denied`; with IPv4 sockets they connect, as `srt` arranges for Java. HTTPS from those sandboxes still cannot verify certificates on macOS, because the system trust service stays out of reach, so a restore from nuget.org in the dependency install fails there: fill the repository's NuGet cache outside the sandbox (`NUGET_PACKAGES=<the cache doctor prints> dotnet restore -m:1`), after which the install and the checks restore from it. On Linux the install downloads packages itself (ADR 0009 addendum).
- `orbit doctor` says up front when a .NET repository's packages cannot be restored inside the sandbox (new `checks.dotnet-packages`, macOS under `srt`): for a repository whose projects have `PackageReference` items (or a `packages.lock.json`, `Directory.Packages.props`, `packages.config`, a local tool manifest, or an MSBuild SDK that NuGet resolves, such as `Sdk="MSTest.Sdk/3.6.0"`), it names the reason in one sentence (the system trust service is out of reach, so .NET cannot verify nuget.org's certificate) and the one command, with the real cache path, that fills the repository's NuGet cache outside the sandbox (the dependency install's own `dotnet restore` with `-m:1`, or `dotnet restore -m:1` of the repository's solution or projects, then `dotnet tool restore` when the repository has local tools, whatever part of them the install restores); the install step and the checks then restore offline from it. It is a warning, and a failure when `dependencies.install_command` restores from the network and that cache is empty, or restores projects while a package version floats (`13.*`, which every restore looks up at nuget.org unless a lock file pins it; doctor names each). The `toolchain dotnet` line says the same of the cache on macOS, for a repository with packages (ADR 0009 addendum).
- A .NET repository that treats warnings as errors no longer fails its dependency install and checks under `srt` on `error NU1900` (#10). NuGet's vulnerability audit cannot reach nuget.org from the sandbox (on macOS nothing there can verify its certificate; on Linux a check has no network unless it lists the host), so every restore warned `NU1900` after a wait, and with `TreatWarningsAsErrors` or `-warnaserror` that warning failed the install and every restoring check even after `checks.dotnet-packages`' command filled the cache, and the base revision's failure became a baseline exception question. The .NET profile now sets `NuGetAudit=false` (MSBuild reads it from the environment; a check's own `env` sets the variable either way) only where the audit cannot run: in every .NET process on macOS under `srt`, and in a check or worker whose sandbox does not let it reach `api.nuget.org`; doctor's probes follow the same rule. Where it can run it stays as the repository configures it, so Orbit does not report green where the repository's CI fails: the dependency install on Linux or in a container, and a Linux check that lists the host in its `network_hosts`, still fail a restore that treats `NU1903` (a package with a known vulnerability) as an error. A check's record says the audit was off exactly when Orbit's setting reached it. A project or MSBuild import that sets `NuGetAudit` itself overrides the environment: the new `checks.dotnet-audit` (macOS under `srt`) fails such a repository when warnings are errors and the install or a mandatory check restores, warns otherwise, and names the change, `<NuGetAudit Condition="'$(NuGetAudit)' == ''">true</NuGetAudit>`, which keeps the audit on everywhere else. `checks.dotnet-packages` no longer says `NU1900` is only a warning, and promises the offline restore only once the audit no longer fails it (ADR 0009 addendum, item 12).
- A `dotnet format` check no longer waits and then becomes a baseline exception question under `srt` (#10). Every form but `dotnet format whitespace --folder` loads the project through MSBuildWorkspace's build host, whose named pipe .NET binds at `/tmp/<guid>` whatever `TMPDIR` says, which the sandbox refuses: on macOS (SDK 9) the format failed after the build host's 60 s connect timeout with a `TimeoutException`, on Linux (SDK 10) at once, and its implicit restore of a repository with project references was refused MSBuild worker nodes (five minutes before the early stop above). Nothing is opened for it: `/tmp` is shared by every process of the user, and Unix sockets in the check's private temp directory would not reach that path. `orbit doctor` fails a mandatory such check before any probe (warns for an optional one) with its command in the form that loads no project, `dotnet format whitespace --folder --verify-no-changes`, ready to paste, reading the folder of the solution or project it named and keeping its `--include` and `--exclude`, and says to run the style and analyzer checks outside Orbit; a check that also builds without `-m:1` gets one command with both changes. With SDK 8 pinned by `global.json`, which loads the project in dotnet format's own process, doctor and the runner refuse only a format that restores first, and name a `dotnet restore -m:1` before it and `--no-restore` (measured under `srt`). The runner reads the build host failure, and a stopped restore of such a check (whose fix it now names as that form, not `-m:1`), as an environment failure, so on the base revision the run blocks with the fix and no baseline exception question. The runner also looks for MSBuild's record of a refused node once a check has failed, so one that fails before its next scan (MSBuild fails at once on Linux) still gets the note and the fix. Under `srt` a check whose `dotnet format` reports the C# or Visual Basic project it names as in no language it supports (`Could not format '<project>.csproj'. Format currently supports only C# and Visual Basic projects.`) is recorded as failed with that fix, not passed: on Linux (SDK 10) that is how `dotnet format` sometimes reports the refused build host, and it exits 0 having checked nothing (8 runs of 40 in an Ubuntu container, and once on GitHub's runners). Workers in a .NET repository are told which form of `dotnet format` runs (ADR 0009 addendum). On macOS not even the folder form runs in a run's check sandbox: it lists every folder above the checkout for `.editorconfig` files, and a run's checkout sits in the read-denied Orbit home, so it died with `UnauthorizedAccessException` for `<orbit home>/worktrees/<key>/<run>` while doctor passed it. There doctor fails every mandatory `dotnet format` check that SDK 9 and later run, the folder form included, and doctor, the runner's note, the block reason and the worker note name running it outside Orbit, in CI, with SDK 8's pinned restore first as the other way.
- A check whose SDK 8 `dotnet format` lost the output of its own `dotnet --version` probe is started again, and its pass is clean. `dotnet format` of SDK 8 reads that version before it loads anything, and when the child exits before it has begun to read the child's output (a race in `dotnet format` itself, also outside Orbit, more likely on a busy machine) it prints `Unable to locate dotnet CLI. Ensure that it is on the PATH.` and exits 4 having checked nothing: once in seven CI runs on GitHub's macOS runners, the pinned restore and `--no-restore` that doctor names for SDK 8 failed so, and reproduced under the runner and `srt` on macOS with SDK 8.0.303 by holding `dotnet format`'s thread after it starts the probe, in a run's checkout and outside it alike. The runner now notes such an attempt and starts the check again, up to two more times beside its `flaky_reruns`; the attempt is kept, and it neither makes the pass flaky nor counts as the check's failure.

- Immutable policy: `.orbit/config.yaml` is validated and frozen into a hashed
  snapshot at run start.
- Isolated workers in git worktrees outside the repository, in the
  `os-sandbox` or `claude-sandbox` tier, with sandbox-runtime or Docker
  isolation for trusted checks.
- Controller-side candidate snapshots, trusted check execution, and evidence
  bound to the candidate tree, check configuration and policy.
- Independent review by a second provider (Codex), with a data-policy gate.
- Adaptive iteration budgets under fixed hard caps; model routing with
  recorded justification; usage and cost accounting.
- Orbit Inquisition for unclear goals, weak evidence and repeated failures.
- Playwright UI journeys with accessibility and visual-baseline handling.
- Delivery through `git` and `gh` with an intent, execute, receipt ledger;
  CI observation and repair.
- Recovery: foreground and service execution (launchd, systemd user unit),
  heartbeats, watchdog, reattachment to workers after a controller crash.
- A learning layer: lesson graph, calibration, prompt overlays with replay
  evaluation and rollback, JSON-LD export, publication guard.
- The `orbit` CLI, eight plugin skills, seven agents and two hooks (a
  SessionStart hook and the guard hook), shipped as one committed bundle
  (`plugin/dist/orbit.mjs`).
